# Liminator

**Liminator** - вспомогательный сервис для подсчета лимитов.

***

### Алгоритм работы

1. **Создание лимита**. Лимит определяется наименованием и может содержать контекст
   (провайдер, терминал и т.п.). Несуществующие лимиты создаются автоматически при HOLD.
   При повторном сохранении лимита используется существующая запись, сохранённый контекст не перезаписывается.

2. **Холдирование (HOLD)**. Заморозка значений лимитов до финализации операции.
   Возвращает значения лимитов на момент операции.

   Если для того же `OperationId` уже есть HOLD хотя бы по одному переданному лимиту,
   запись повторного HOLD пропускается целиком: исходные значения и контекст сохраняются,
   дополнительные лимиты из запроса не создаются. После этого возвращаются значения лимитов.
   Для непересекающегося набора лимитов тот же `OperationId` можно использовать повторно.

   Возможные ошибки:

   - _DuplicateOperation_ — одно имя лимита передано несколько раз внутри запроса.
     Запрос отклоняется до получения блокировки и создания лимитов.
   - _OperationAlreadyInFinalState_ — для связки `LimitName` + `OperationId` уже есть COMMIT или ROLLBACK.
     Эта проверка выполняется до проверки повторного HOLD и создания недостающих лимитов.
   - _LimitsValuesReadingException_ — ошибка при получении значений после выполненного HOLD.
     Можно повторно запросить значения или повторить исходный HOLD: существующая запись будет сохранена.

3. **Финализация операции (COMMIT/ROLLBACK)**. Применение или отмена замороженного значения.
   Повторная финализация в том же состоянии не создаёт новых записей;
   при повторном COMMIT проверяется совпадение значений по модулю с сохранёнными.
   Если завершена только часть переданных лимитов, финализируются оставшиеся.
   Все состояния и значения проверяются до записи: ошибка по одному лимиту отклоняет весь запрос.

   Возможные ошибки:

   - _LimitNotFound_ — хотя бы один переданный лимит не найден.
   - _InvalidRequest_ — имя лимита повторяется внутри запроса COMMIT/ROLLBACK;
     для ROLLBACK эта ошибка также возвращается, если не найден ни один переданный лимит.
   - _OperationNotFound_ — отсутствует HOLD по одному из переданных лимитов, операция уже завершена
     в другом состоянии или значения COMMIT не проходят проверку: превышают HOLD по модулю
     либо отличаются по модулю от ранее сохранённого COMMIT. Эта же ошибка возвращается,
     если в проверяемой истории найдены дубли для одного лимита и состояния.

4. **Получение значений по лимитам**. Можно получить значения на момент определённой операции
   или последние актуальные значения. Несуществующие лимиты не включаются в ответ.

   Возможная ошибка:

   - _LimitsValuesReadingException_ — ошибка при получении значений лимитов.

### Одновременные запросы

HOLD, COMMIT и ROLLBACK с одинаковым `OperationId` обрабатываются последовательно.
Проверка состояния операции и запись изменений выполняются в одной транзакции.
Ожидающий запрос проверяет состояние после завершения предыдущей транзакции.
Ключ транзакционной advisory lock вычисляется в Java как 64-битная часть SHA-256
от namespace и `OperationId`; теоретическая возможность коллизий сохраняется.

Таймаут ожидания блокировки задаётся параметром `service.operation-lock-timeout-seconds`:
в `application.yml` установлено 2 секунды, при отсутствии настройки используется 4 секунды.
Транзакционный `lock_timeout` ограничивает каждое ожидание блокировки отдельно,
включая блокировки при создании общих лимитов и контекста. Это не общий таймаут операции.
При превышении лимита изменения транзакции откатываются; запрос можно повторить после
освобождения блокировки. Настройка не сохраняется в соединении после завершения транзакции.
